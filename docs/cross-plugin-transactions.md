# 生活写入的跨库交接（设计中）

本说明记录实现前必须解决的一致性约束；当前代码没有完成下面的协议，不能据此切换生产。

隔离测试确认，原本在新归属下启动梦境会在材料收集阶段遇到跨库读取限制，并可能过早消耗当天的首次写作尝试。开发版现先固定生活库快照，再进入主库快照或事务；日记材料收集、写作任务校验、模型预算和保存使用该顺序，且不会把生活库锁跨异步模型等待保留。提供方不支持快照时，在预留写作尝试之前暂停。该连接只在隔离双库及模拟提供方验证，其他联合快照、真实事件消费者和生产切换仍未完成。

生活事件现可通过同一提供方租约读取：宿主核对原事件、角色、会话、活动版本、来源和已提交的原操作后，在同一主库事务中写入去重回执和持久收件箱；生活库只在核验宿主回执后确认投递。宿主梦境消费者可从收件箱恢复，已有结果不明的模型任务不会因重启再次调用。日记材料直接从生活账本读取，兴趣和换装消费者仍待实现。活动回退演练会阻止收件箱中尚未完成、失败或结果未知的事件被忽略。

新插件已有独立可测的 `PreparedCommands` 基础：它保存带内容摘要的待决定记录，对同一角色限制一个未决命令，并在生活库同一事务内提交本地效果、命令结果和生活事件。决定必须由主插件能力确认，确认回调在新库事务之外执行；重放同一已确认决定不重复写入。生活库落库后，角色锁会保留到主插件确认操作回执，避免中途重启时后续命令越过未完成的交接。

主插件新增独立的持久决定基础，使用现有的 `runtime_metadata` 和操作审计，在同一主库事务中验证调用方提供的授权结果、写入决定及主库本地效果；只有核验生活库已落库后才能完成主插件回执。重启后可按原会话、命令 ID 和内容摘要查回决定。跨库查询回调均在对方数据库事务之外执行，避免互相等待锁。模拟测试使用两份独立 SQLite，覆盖中断恢复、授权拒绝、事务回滚、角色并发、审计或请求内容变化和事件去重。

这些基础尚未接入生产中的活动或日程写入。具体调用方仍须提供实际授权与来源复核，且主库中待提交的业务效果和提醒不能提前对外可见或投递；联合快照也尚未实现。不能仅凭这些测试切换生产。

隔离演练新增了一条活动状态变更路径：新插件按原所有者、版本和状态规则计算新记录，写入活动头、历史及原操作回执；在主库确认原 `role.life` 操作完成后，才允许接口读取该角色的新版本并创建完成事件。确认期间其他角色的单独读取仍可继续，但全局回执扫描暂缓，避免扫描游标跳过未确认记录。主插件演练代码复核原角色、会话、操作编号、权限及阅读原文，不允许跳过非空原文；来源撤回后仍可暂停。完成状态要求宿主同步验证原执行证据。测试使用合成活动和两个独立库，并以测试回调模拟执行证据；真实模型／平台证明、业务调用方和实际执行器尚未接入。

主插件应用和日记服务现在共用一个活动账本归属入口。默认与原来一样使用主库；若将来完成停写迁移并选择新归属，读取只走绑定的生活提供方，绑定解除会使旧回调失效，主库事务与读快照内禁止跨库读取，未迁出的写入会拒绝。主插件的两种宿主会在会话创建时绑定当前注册代次，提供方注册、注销或宿主关闭也会更新或撤销租约；已进入的回调可结束，但结束前不能注册替代提供方。测试覆盖加载顺序、会话重建、回调内注销和暂时不可用后恢复。这个入口不会自行设置归属标记，新插件仍未注册真实提供方；联合快照、所有直接 SQL 调用方及实际活动写入仍未完成，当前不能启用新归属。

旧生活协调器在活动归属转移或归属无效时不再推进阅读、浏览和睡眠，并取消仍在运行的旧工作；手动调用旧阅读或睡眠入口也会拒绝。归属转移后仍保留主插件日记日程的配置刷新与注册。正式切换仍必须先停写并等待或处理在途调用，不能依赖门控替代一致性备份或新执行器、事件消费者和恢复流程。

旧日程规划器也受日程归属控制：转移后停止自动规划并取消旧任务，手动规划和既有任务复核会在模型调用前拒绝。主插件先启动且新提供方未绑定时，不再因扫描旧规划上下文而阻断启动。新插件的日程规划调度、批量写入和恢复仍未实现。

隔离生活库现也支持准备睡眠或浏览活动创建：每个角色串行准备，检查现有睡眠、阅读和原会话的活动；主库确认前新活动不经提供方读取。测试串联主插件实际身份与 `role.life.run` 授权，覆盖准备后撤销授权、跨会话篡改、两次生活库重开、记录被改写以及创建后暂停。此授权只覆盖身份和执行许可，不替代自动日程、配置、平台可用性或手动管理操作权限检查；生产执行器和插件生命周期仍未使用该路径。

阅读记录删除已有隔离交接：主插件复核管理身份、页面令牌、原角色和记录版本，在同一主库事务中撤回来源、保留管理及关联片段操作回执并决定提交；新库在一个事务中删除活动和历史、取消同一原文下尚未开始的片段，并保留逐行摘要及原生活回执。主库确认前读取该角色和扫描全局回执均会等待；中断后可用原请求继续，尚未决定时可以明确取消准备。完成后重放相同命令不会重复删除；已准备的旧格式单条删除也能恢复。回退演练检查摘要、主库决定、管理审计及来源撤回状态后，才接受已删除的原记录缺席。开发版管理命令已接入此交接，并通过模拟提供方验证授权、撤回、人工重试和去重。进行中或暂停的关联阅读仍会阻止删除；工作任务取消和后台自动恢复尚未接入，因此还不能切换生产。

隔离演练还覆盖了日程创建和带提醒的修改：生活库计算并保存版本、历史与原操作回执，主库决定后用测试专用标记暂停模拟提醒，主库确认时处理模拟取消并完成原回执；生活库在确认前不通过读取接口暴露新版本。两库重启、重复执行、跨所有者重名以及版本被篡改均有测试。这里的提醒标记与取消是测试夹具，不是真实提醒调度器；实际调用方仍须校验所有者、会话、来源、操作参数及提醒，建立真正的投递屏障后才能接入。

主插件另有一套待接线的实际提醒暂缓机制：在主库事务中按提醒及生活决定持久化标记；已有提醒任务正在执行、已被平台接收或结果未知时拒绝建立暂缓。暂缓期间不新建该提醒的投递任务，已排队的原任务保持原状态和截止时间；并发取任务或关闭等待器时也不把它误判为失败，其他提醒继续运行。主插件重启后暂缓标记和原排队任务保留。此机制已在隔离宿主测试，只有未来的真实日程命令在授权和来源复核后把决定、暂缓和原操作保留在同一主库事务中，并在最终处理提醒时解除暂缓，才能形成完整交接；现在生产命令尚未调用它。

主插件的 `CalendarHandoff` 现可对已准备的日程请求编排授权、原操作预留、提醒暂缓、生活库提交、主库确认和解除屏障；它通过受限回调核验另一侧的持久状态，不把主库连接传给生活插件。隔离双库集成测试将该代码与真实宿主提醒队列、操作审计和提醒取消串在一起，覆盖生活库重开、事务中断回滚和同一命令重放。测试使用合成数据及 `staged_*` 表，旧日程入口和实际插件生命周期尚未调用它。

`CalendarCommandBridge` 已将新建和修改等命令转换为上述交接，并在隔离测试中处理旧主库操作回执重放、准备后来源撤回、主库决定后或生活库提交后的中断与重跑。它目前只使用演练表，要求调用方事先确认跨窗口旧版角色计划已完成归属迁移；这个前提尚未由正式迁移工具证明，因此不能接入生产入口。

日程读取与单条命令还提供了受限的版本化提供方转发：隔离测试经真实注册表和宿主日程入口完成修改、重放、注销和重新绑定，注销后的旧租约不能调用新实例，也不回读旧库。测试显式提供模拟的归属确认；生产切换仍须由正式迁移流程核实并持久化该凭证，不能把测试中的确认当作线上证据。

主插件的日程读写入口在隔离测试中共用持久归属标记和生活提供方绑定；未设置标记时保持旧行为，标记为新插件但提供方缺失时拒绝读写，解绑等待进行中的读写调用完成，重新绑定也不会让旧读取租约恢复有效。读取代理在宿主复核原角色、会话与来源后访问生活库，旧库只用于经宿主验证的跨窗口旧角色计划归属映射。隔离测试手动设置标记进行验证，代码不会自行切换归属。尚未迁出的提醒创建会明确拒绝；主库事务或读快照内的生活库读取也会停止，因此现有提醒投递读取等调用方仍需改造。跨窗口旧计划正式迁移、其他直接读取主库的调用方、插件绑定与重启恢复均尚未完成；正式迁移工具必须先暂停写入并等待在途调用结束，不能现在写入该标记。

现有自动规划会在一个主库事务中取消旧计划、创建多个新计划并完成模型任务回执。新的单条日程交接不能嵌在该事务内：主库回滚无法撤销已提交的生活库写入。当前入口和协调器会拒绝在主库写事务或读快照内调用；正式切换前需要实现并验证整批规划的持久决定、原子可见性与恢复，不能简单逐条提交造成半批日程。

主插件已有待接线的日程授权能力，核对角色、会话、原操作编号、存储归属、版本、时间和来源，并在决定前复核日程访问、来源有效性与原提醒的取消权限。隔离测试使用真实权限和来源仓库，覆盖准备后撤回来源、跨角色与跨会话篡改、未来时间，以及模拟提醒权限拒绝；拒绝后不会写入主库决定或完成回执。业务命令仍须实际调用该能力并编排准备、决定、提醒暂缓、提交和恢复。

## 现有原子边界

- 阅读完成在主插件同一事务内校验角色、原文版本和受众，并写入活动版本及操作回执。阅读开始还在同一事务内更新节奏标记、清除已授权重试标记。
- 开始睡眠在同一事务内检查该角色现有的睡眠与阅读，再创建睡眠活动。多个会话共享一副身体，按会话加锁不足以阻止同时入睡。
- 日程命令在同一事务内校验授权和来源，并写入版本与回执；提醒的创建或取消还会修改主插件的提醒记录。
- 对话时间线在主库读快照中合并活动、日记和成长。独立读取两个 SQLite 库并分别取当前最大序号，不能保证得到同一时点的联合快照。

若直接把活动或日程写入改成跨插件调用，主库随后回滚时新库可能已经提交；反过来只提交主库也可能留下错误的阅读节奏、被消费的重试许可或提前可投递的提醒。两次独立 SQLite 提交不能伪装成一个原子事务。

## 待实现的交接顺序

1. 主插件验证并封装原角色、会话、操作 ID、预期版本、来源和命令参数。新插件在自己的事务中校验命令、持久化不可变的待决定记录，并按角色串行化相互冲突的生活写入。准备阶段不得把新版本或事件暴露为已完成。
2. 主插件重新验证角色、会话、授权、来源版本及相关主库状态，在一个事务中持久化不可变的提交或取消决定，以及相应的主库本地变更和操作审计。不得在事务内等待新插件回调。尚未获得新库确认的提醒不得投递，外部消息和社交操作不得作为此事务中的效果。
3. 新插件读取已持久化的决定，在自己的一个事务中提交活动或日程的新版本、命令回执和生活事件，或释放被取消的准备记录。按操作 ID 及参数摘要去重；相同操作的不同参数必须拒绝。
4. 主插件确认新库结果并完成原有操作回执。重启时从持久记录恢复：没有主插件决定时保持准备状态，不能猜测提交或取消；已有提交决定时只重放可幂等的本地落库；已有完成回执时不重复应用。模型调用、消息和社交操作的未知结果继续遵循原有审计，不因本协议自动重试。
5. 在联合快照设计完成之前，不允许把时间线切到两个独立存储。读路径必须同时保留来源撤回与权限复核，不能以旧活动表作降级结果。

准备记录必须能在插件重载后恢复，冲突操作不能绕过角色级排队；切换、停用或回退时要等待或明确保留所有未决记录。实现时还要核对删除、普通经历、材料引用、重复日程、提醒、阅读恢复与睡眠跨会话互斥，而不仅是活动状态更新。

## 必须测试的中断点

针对每种代表性命令，分别在准备前、准备后主库决定前、主库提交决定后、生活库落库后、主库确认前中断并重启；核对版本、节奏标记、重试许可、提醒、事件及操作回执。还须覆盖同 ID 不同参数、并发会话、来源或权限在准备后发生变化、提供方停用与恢复、旧版本、未知社交结果，以及已产生新数据后的回退。
