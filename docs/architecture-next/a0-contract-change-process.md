# 契约变更流程

适用 `[03]` 与 `good_life/contracts/`。当前 `CONTRACT_VERSION=2`（coordinator 已批准 batch 1：V2-01/02/03/07/08；04-06 延至 A7），状态 frozen；v1 声明与 wire 继续兼容支持。类型声明不表示提供方已经支持该版本或全部能力。

1. 开始任务时记录基线提交、契约版本、自己允许修改的模块。普通功能代理只消费冻结版本；发现不够表达业务时，在自己 PR 描述提出变更，不在自己的 worktree 悄悄修改公共类型或复制一个近似类型。
2. 变更申请写明：具体冲突和场景；旧→新字段/枚举/签名 diff；涉及生活/宿主/存储/消费者；旧数据及在途任务如何读取、恢复和回退；适配及测试方案。不要把未确认的方案作为并行任务的依赖。
3. 指定单一契约维护分支串行处理申请，A0 负责人维护它。**契约审批人是项目统筹者；未指定统筹者时由用户审批**。涉及权限、来源、事件 wire、宿主端口的变更，还需宿主实现负责人评审；影响领域效果/状态需对应唯一拥有者评审。代理的建议和消息不等于用户批准，也不赋予部署或配置权限。
4. 版本规则：仅修错字、补不改变含义的例子或映射证据可保持 v1；任何字段、类型、默认值、枚举成员、转移边、端口签名或含义变化都形成下一整数契约版本，并同步 03 与 CONTRACT_VERSION。新增 Enum 成员对穷举消费者也是变更；不得说“只新增所以不升级”。原协议/数据库版本仍各自独立，架构升版不自动升旧 wire。
5. 兼容规则：新版本提供明确 adapter/能力协商、默认与 null 规则及旧在途版本支持期限；新字段只有接收方允许扩展才可发送。现有 strict companion.life.v1/event wire 不加字段、不改同步性；采用新能力/协议标识显式协商。移除/重命名/改变单位或状态语义，先给兼容读与转换，不能重置状态、重做 unknown 操作或扩大来源受众。禁止为省事全库“升级”未知旧事实。
6. 契约 PR 一次包含 03、类型/Protocol、迁移映射、受影响文档、枚举/序列化/转移及兼容测试、调用方清单。审批后先合入契约 PR（是否合并由统筹者安排），再通知并行任务 pin 新提交与版本、rebase 并复跑相关测试；有冲突由契约维护者裁决，不按最后写入者覆盖。未切换任务继续 pin 旧提交，不能混合声称同一版本。

合入检查：声明与文档一致；既有 v1 同步接口未变；旧回执和在途操作可恢复；所有受影响拥有者已确认；测试真实结果和未覆盖项已列出。没有业务变更需要时，不因本流程额外要求用户批准普通局部实现。

`[03]` 指 [公共数据契约](03-shared-contracts.md)。本流程不授权合并、部署或更改生产归属标记。
